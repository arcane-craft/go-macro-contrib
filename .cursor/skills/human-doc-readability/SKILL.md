# 人类可读文档

## 使用时机

用户希望文档「更好读」「少 spec 腔」「新人能跟着做」或优化 README / 入门指南时，按本 skill 执行。

## 工作流程

### 1. 明确文档类型与读者

| 文档 | 优化目标 |
|------|----------|
| README / 快速上手 | 能完成最小可行流程 |
| 开发指南 / API 文档 | 契约正确、集成细节可查 |

### 2. 搭建分层大纲（建议 3～4 层）

- **L0 开篇**：一两句话说明项目是什么，不写实现细节。
- **L1 快速上手**：按新人真实顺序列出可执行步骤。
- **L2 工具与配置**：命令、CLI、编辑器配置；配置项须说明**为什么**要这样设。
- **L3 参考**：模块结构、可选依赖、本地联调、排错、进阶主题。

**快速上手** 必须出现在 **参考 / 附录** 之前；不要把迁移说明、长篇背景插在步骤中间。

### 3. 用自然语言重写正文

- 以项目主语言（常见为中文）书写，避免 RFC / OpenSpec 口吻。
- 将「MUST / SHOULD / MUST NOT」「不是 xxx」「切勿 yyy」等改为正面指引：**你需要… / 你可以… / 建议…**
- 句子须有明确**主语**，避免说明书式无主句。

### 4. 控制「原理 / 背景」段的信息量

- 原理段只建立心智模型，不堆实现级名词。
- 细节、边界条件、内部对齐说明放到专门章节或其它文档。

### 5. 示例与命令的表述范围

- 若示例位于独立示例仓库或子目录，应写为**对照示例、可复制模式**，勿写成「全局官方长期命令」。
- 全文命令、路径、代码块须前后一致。

### 6. 删减对终端读者无用的内容

- 移除或迁出：规范对齐过程、无行为变更类 meta、仅维护者关心的叙事。
- 历史迁移、BREAKING 对照表放在 CHANGELOG / 迁移指南，除非用户明确要求留在 README。

### 7. 配置项要写清原因

说明默认行为下读者会遇到什么问题，以及配置后改善什么（例如：文件是否出现在工程视图、补全、类型检查）。

### 8. 交付前自检（新人视角）

- [ ] 从开头读到快速上手结束，能否不翻附录就完成第一次成功？
- [ ] 是否仍残留大量规范腔、否定式堆砌或未解释的「魔法命令」？
- [ ] 术语是否统一、链接是否有效、步骤顺序是否符合认知（先准备环境/工具，再写一行脚本）？

### 9. 输出方式

- 用户指定了文件：做**最小范围**改写，不扩写无关章节。
- 未指定范围：先问清要改哪些文档（仅 README、README + 作者指南等）。

## 文档类型分工（勿混在一处）

| 文档 | 职责 |
|------|------|
| README | 定位、概要、上手、常用命令、深读链接 |
| 开发 / 集成指南 | 契约、扩展点、错误处理、进阶 |
| 规范（OpenSpec 等） | 可检验的 MUST/SHOULD 与场景 |

用户文档改叙述后，若与规范冲突，应提示同步更新规范或标明以哪份为准。

## 示例

### 规范腔 → 用户语言

**不佳：**
> MUST NOT 依赖 `-tags dev`

**更佳：**
> 日常构建通常不需要加 `-tags dev`。

### 补全主语

**不佳：**
> 会生成配置文件。

**更佳：**
>  CLI 会在当前目录生成配置文件。

### 教学顺序

**不佳：** 开篇只写 `make generate`，未说明生成器从哪来。

**更佳：** 先写「安装 CLI / 初始化项目」，再写 `make generate`，并说明 generate 调用的是哪条命令。

## 一句话原则

**人类可读 = 短入口 + 按任务分层 + 先懂再动手 + 自然语气 + 配置有原因；边界与可验收行为留给规范，主文档负责把人带到第一次成功。**
